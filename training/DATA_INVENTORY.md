## 2. Processed Parquets (`data/processed/`)

All parquets share the same 75-column schema:
- **73 feature columns** (see note on inter-request features below)
- `label` (int: 0=benign, 1=sqli, 2=xss, 3=path_traversal, 4=cmdi)
- `sample_id` (string, source prefix + index)
- `timestamp` (all = 2026-06-08, synthetic — not usable)

**⚠️ R1 VIOLATION:** These parquets were generated by a **Python extractor**, not the TypeScript extractor mandated by PLAN.md R1. All 75 feature columns were computed in Python. When the TS extractor (tasks 1.2–1.7) is implemented, every dataset must be re-processed through `extract --in dataset.jsonl --out features.csv` to ensure production/training parity.

**⚠️ Inter-request features to exclude:** Columns `status_code`, `req_count_1s`, `req_count_5s`, `req_count_60s`, `error_rate_4xx_60s`, `endpoint_diversity_60s` are response/behavioral features. `status_code` is a response field (unavailable at middleware intercept time). The req_count/rate columns require inter-request state (out of scope per project definition). Effective intra-request feature count = **66 features**.

## 6. Recommended Parsing Priority Order

Re-run extraction via TS extractor CLI (after task 1.7) in this order:

1. **`data/owasp/`** — 56,504 real HTTP requests with CRS labels. Full URL/header/body structure. Best structural diversity. Provides full HTTP context. Priority parser needed. No benign — must supplement.
2. **`data/data_capec_multilabel.csv`** — 907,815 rows once the parser bug is fixed. Full HTTP request fields. Will dominate the final dataset. Fix CAPEC-ID → {sqli,xss,pt,cmdi} label mapping. Multi-label rows need a resolution strategy (e.g., pick highest-priority label, or one row per active label).
3. **`data/Payloads.csv`** — 43,217 rows with full URLs. Good for XSS. Requires label splitting: strip `<br>` artifacts, re-classify Malicious rows as xss (most are URL-embedded XSS).
4. **`data/modsec-learn/`** — 508,530 benign + 30,544 malicious query strings. Huge benign pool for IF training. Malicious = sqli only (assumption).
5. **`data/payload_full.csv`** — 31,067 rows, only dataset with all 5 classes (including 89 cmdi). Small but complete taxonomy.
6. **`data/XSS_dataset.csv`** — 13,686 rows. Benign (Wikipedia) useful only to widen benign distribution; XSS snippets lack HTTP context.
7. **`data/command injection.csv`** — 2,106 rows, 515 cmdi samples. Small but critical for underrepresented class.
8. **`data/omurugur PT wordlists/`** — 43,137 path strings. Useful for path_traversal augmentation. No HTTP context.
9. **`data/russellmitchell/`** — 3,435 rows. Attack labels don't map to target classes. Use non-attacker rows as benign only.

## 7. Balancing Strategy Recommendation

Given cmdi has only ~2,898 clean samples vs benign ~127,802:

**Primary:** `class_weight='balanced'` in RandomForest — lets all samples contribute without data generation. Zero risk of synthetic sample leakage across train/test.

**Secondary (for cmdi only):** SMOTE on the training set only, after splitting. Target: ~8,000–10,000 cmdi samples. Apply only to train partition. Never on val/test (R2).

**Rationale:** Breiman (2001) showed RF is robust to imbalance with class weights. SMOTE (Chawla et al., 2002) is justified only for severe ratios >10:1, which cmdi hits (benign:cmdi ≈ 44:1 on clean data). Do not apply SMOTE to xss (9:1 manageable with weights alone).

**Do NOT:** Undersample benign heavily — IF training needs large benign pool.
