# ML Readiness Assessment
**Date:** 2026-06-10  
**Decision gate:** Can we proceed to F2 (dataset unification)?

---

## 1. Readiness Verdict

**BLOCKED — Cannot proceed to F2 training as-is. Must resolve blockers first.**

The `dataset_final.parquet` is not usable: 78.3% of rows have all feature values = 0. Proceeding to training on this data would produce a model that learns "zero feature vector → class label", invalidating all reported metrics.

---

## 2. Blockers

### BLOCKER 1 (Critical): data_capec feature extraction is broken
**Evidence:** `data_capec.parquet` — 905,069 rows, 100% of feature columns = 0.0. Only `status_code` has non-zero values (derived from response field, not the request).  
**Root cause:** The Python parser for data_capec_multilabel.csv did not correctly extract text from the request fields into the extractor's input. The extractor received empty strings and produced zero vectors.  
**Impact:** 78.3% of `dataset_final.parquet` is corrupt. All capec SQLi (250,230), capec path_traversal (18,005), and capec cmdi (7,090) are zero vectors — they would teach the RF to classify zero features as attacks.  
**Fix required:** Re-write the capec parser to correctly construct CanonicalRequest from `request_http_method`, `request_http_request`, `request_body`, and header columns. Re-run feature extraction.

### BLOCKER 2 (Critical): R1 violation — features computed in Python, not TypeScript
**Evidence:** All parquets in `data/processed/` were generated by a Python extractor. No TypeScript extractor exists yet.  
**Impact:** Even if capec is fixed, the feature vector used for training differs from what the TS extractor will produce in production. Any model trained on these parquets has invalid metrics from day 1.  
**Fix required:** Complete tasks 1.2–1.7 (TS extractor), then re-run all dataset parsers through `extract --in dataset.jsonl --out features.parquet`.  
**Note:** The existing Python parquets are still valuable as a reference implementation to verify TS extractor output against (gate 1.6).

### BLOCKER 3 (High): cmdi critically underrepresented in clean data
**Evidence:** Only ~2,898 clean cmdi samples after excluding broken capec. Target: ≥5,000 for viable F1 ≥ 0.80.  
**Fix required:** Fix capec parser (adds ~7,090 cmdi) + SMOTE augmentation on training set only.

### BLOCKER 4 (Medium): owasp_logs has zero benign samples
**Evidence:** `owasp_logs.parquet` label distribution = {3:49849, 1:4064, 4:2331, 2:260, 0:0}.  
**Impact:** owasp is the best full-HTTP-structure dataset but provides no benign training data. IF training pool is reduced.  
**Fix required:** Confirm whether the OWASP log parser intentionally excluded benign (non-triggered) requests. If not, re-parse to include 200 OK responses with no rule matches.

### BLOCKER 5 (Medium): russellmitchell attack traffic mislabeled as benign
**Evidence:** All 3,435 russellmitchell rows in parquet have label=0. Raw label files show `attacker_http`, `dirb`, `service_scan` categories.  
**Impact:** Attack requests (which include scanning and directory traversal) are in the benign training pool.  
**Fix required:** Either correctly exclude attacker-flagged rows from benign, or re-label `dirb`/`attacker_http` rows as path_traversal/generic attack.

### NON-BLOCKER (Documentation): status_code and req_count_* must be excluded from feature vector
**Evidence:** These 6 columns are response/inter-request features, all=0 for most datasets, unavailable at RASP intercept.  
**Action:** Drop before training. Feature vector = 66 dimensions (75 - label - sample_id - timestamp - status_code - req_count_1s - req_count_5s - req_count_60s - error_rate_4xx_60s - endpoint_diversity_60s = 66).

## 4. Recommended Balancing Strategy (final)

**RF training:**
- Use `class_weight='balanced'` as baseline in all experiments.
- Apply SMOTE to cmdi on train partition only (after split) to reach ~8,000–10,000 samples. Cite Chawla et al. (2002).
- Do NOT apply SMOTE to other classes — weights alone sufficient.
- Report class weight multipliers in experiment log.

**IF training:**
- Train exclusively on benign samples from train partition (~105,000–126,000 after 70% split).
- Target benign pool is dominated by query-string-only records (modsec_learn) — note this structural bias in threats-to-validity.

**Specifically:** Extract `request_http_request` (URL path+query), `request_body` (NaN→""), and all header columns. Pass through extractor as `CanonicalRequest`. Verify that at least `payload_length > 0` for rows with non-empty request fields.

**What:** Start tasks 1.2–1.5 (structural + semantic + encoding features). Pick 1,000 rows from `owasp_logs.parquet` (which has good existing features), pass through TS extractor CLI, compare output to existing Python-computed values.  
**Verification:** Gate 1.6 — max absolute difference < 0.001 per feature dimension per sample.

### Action 3: Fix owasp log parser to include benign traffic

**Verification:** New parquet has label=0 rows. Estimate: ~30–40% of owasp requests may be benign probes blocked by bot rules (like the DotBot example in the first log sample), which should still count as benign from an attack-pattern perspective.
